# HTML Vault Dogfood Notes

Status: active empirical feedback from HTML Vault macOS/iOS dogfooding.

Purpose: capture the places where viewing Capsules inside HTML Vault exposed format,
compiler, and host-contract pressure. This file is intentionally not a replacement
for `CAPSULE_SPEC.md`; it is a staging area for findings that may become spec,
validator, compiler, or prompt changes after more examples.

## Summary

HTML Vault is exercising Capsules as real portable documents inside native Apple
hosts. That revealed a useful split:

```text
Capsule spec        = output contract
Reference compiler = reliable way to produce or repair that output
HTML Vault         = custody host, validator, viewer, and optional workshop
```

The important design conclusion is that the reference compiler should become more
useful without making compiler-generation mandatory. A valid Capsule can still be
hand-authored, LLM-authored, generated by Python, generated by Swift, generated by
Rust, or repaired by Vault. The validator decides conformance.

## What Vault Proved

### 1. Presentation declarations are necessary

The iOS Vault app could not reliably infer whether a Capsule wanted a reader,
mobile card, feed, slide deck, or story surface. Guessing led to wrong views and
duplicated controls. Declared `presentations[]` solved the main problem: Vault can
surface only the views the Capsule says exist.

Observed useful fields:

```json
{
  "id": "mobile_story",
  "profile": "reel",
  "entry": "#capsule-reel",
  "navigation": "sequence",
  "chrome": "capsule",
  "required": true
}
```

This supports the current spec direction: hosts should not infer undeclared views.

### 2. Chrome ownership is real, not cosmetic

On iPhone, Capsule-owned story chrome and host-owned app chrome can easily overlap.
`chrome: "capsule"` lets the host recede so the Capsule can own play/pause, story
progress, view labels, and close/replay controls. When `chrome: "host"` or
`chrome: "none"` is declared, Vault can safely provide its own minimal navigation.

Dogfood rule:

```text
If chrome="capsule", the host should not duplicate presentation controls.
If chrome="host", the Capsule should not render competing app-like controls.
```

This does not mean the host loses custody controls. It means custody controls move
outside the declared presentation surface, collapse behind a menu, or appear only
on explicit user gesture.

### 3. Story/reel views need stronger producer guidance

Locked mobile story views exposed mobile-specific failure modes:

- accidental pinch zoom
- text selection/copy handles on long press
- scroll bounce fighting one-screen slides
- duplicated back/play/settings chrome
- story timer not restarting after "Back to start"
- end screen preventing backward navigation

Most of these are template/compiler problems rather than new manifest fields. The
current lean is:

```text
Do not add a normative "locked_story" manifest field yet.
Represent this as compiler/template behavior or as data-level presentation_model
metadata until multiple independent producers need the same field.
```

Hosts may still use generic heuristics: for `profile: "reel"` +
`navigation: "sequence"` + `chrome: "capsule"`, a mobile host may disable pinch
zoom, reduce surrounding chrome, and treat the presentation as immersive.

### 4. Runtime remains enhancement, not source of truth

Safe Preview and iOS no-JS/limited-JS behavior showed that the root reader layer
must remain useful. The best Capsules had a strong readable `#capsule-root` and
used story/slides/mobile views as derived alternate presentations.

This reinforces the existing Rule 12 language:

```text
Runtime may enhance, transform, filter, search, export, or visualize.
Runtime must not be the only path to understand the artifact's primary meaning.
```

### 5. Chat-window generation is useful but needs trust tiers

A recent chat-window Capsule candidate used an ad hoc Python script to assemble
the file. It produced a mostly conforming Capsule candidate but failed the final
integrity check because it used the all-zero hash sentinel. That is a good result
for dogfood, but it should not be confused with reference compiler output.

Recommended producer tiers:

```text
Bronze: raw/LLM Capsule candidate
  - may have provisional all-zero integrity hash
  - may need validator repair
  - generator.kind: "llm"

Silver: hybrid/chat-tool candidate
  - LLM plus ad hoc Python/JS/helper assembled the HTML
  - still not canonical unless it uses official hashing/validation
  - generator.kind: "hybrid"

Gold: reference compiler or repair output
  - official compiler produced/repaired final HTML
  - canonical hash verifies
  - generator.kind: "compiler" when the compiler owns final assembly
```

The spec should remain producer-neutral. The reference compiler should be the
recommended path for repeatability, not a requirement for validity.

### 6. Python is good as a compiler, risky as a hidden compiler

Python is appropriate for deterministic chores:

- UUID generation
- QR generation
- JSON canonicalization/escaping
- template rendering
- capability/presentation consistency checks
- integrity repair

But ad hoc per-chat Python creates drift if every model invents a new builder.
The safer flow is:

```text
LLM creates source JSON or a provisional Capsule
        ↓
reference compiler/repair tool
        ↓
validator
        ↓
Vault ingest/export
```

This preserves the "from scratch" charm while giving users a reliable path to a
fully conforming artifact.

## Immediate Spec/Tooling Alignment

These dogfood findings already produced concrete alignment work:

- `derived_from[]` is documented in the full spec and should also live in
  `spec/manifest.schema.json`.
- The chat-window prompt should use `print_to_pdf`, not bare `print`, because the
  controlled capability vocabulary already names the print export capability
  `print_to_pdf`.
- Chat-window prompt guidance should distinguish `llm`, `hybrid`, and
  `compiler` generator tiers.

## Candidate Next Work

### Reference compiler UX

Create a narrow, LLM-friendly command path:

```bash
python3 compiler/compile_multiview_demo.py examples/source.json --out capsule.html
python3 compiler/validate.py capsule.html
python3 compiler/repair_integrity.py capsule.html --out capsule.repaired.html
```

The exact command names can change, but the product idea is stable: LLMs should
feed structured source into an official compiler rather than reinvent final HTML
assembly each time.

### Vault integration

HTML Vault can act as a workshop without owning the format:

- Validate Against Capsule Spec
- Repair Integrity Hash
- Normalize Manifest
- Generate/Compile Views
- Export Derived Capsule

Vault must preserve originals and produce derived Capsules that still conform to
the Capsule spec. Derived Capsules should use `parents[]` when the source is a
Capsule and `derived_from[]` when the source is a non-Capsule chat/document/data
source.

### Presentation template guidance

Strengthen compiler templates for:

- mobile safe-area handling
- one-screen story layout
- reduced motion
- no pinch zoom for locked story surfaces
- no long-press text selection when a surface is intentionally app-like
- tap-left/tap-right/back-to-start behavior
- clear separation between Capsule chrome and host chrome

These should start as template conventions, not required spec fields.

## Current Lean

1. Keep the fixed five-block Capsule envelope.
2. Keep `presentations[]` optional and declared-only.
3. Keep `chrome` as the host/capsule control boundary.
4. Keep compiler use recommended, not mandatory.
5. Treat chat-window/ad hoc Python output as dogfood candidate tier unless it
   passes through the reference compiler/repair path.
6. Do not add more manifest fields for mobile-story behavior until there is
   repeated pressure across independent producers.
