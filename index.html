Observation 1

Observation 1: HTML has emerged as a key substrate* for AI-assisted work.

* I know, I know — "substrate" is overused.

Two leading voices, same direction:

Question 1

Question 1: How do I get HTML out of my LLM?

Answer 1a

Vague approach · just ask the LLM

Answer 1a: Just ask the LLM for HTML.

Two voices in the wild, same shape — both pointing at the same vague-but-functional default of telling the LLM you want HTML:

This works for one-off viewing. The LLM produces some HTML, the bytes render in a browser, you can read what's there. But what you actually get is unstructured HTML: no manifest, no identity, no integrity guarantees, no contract on what's inside. The file can't say what it is, where it came from, what tool made it, what version it represents, or whether it's been modified. Fine for "show me what you mean" — lossy for everything else (which is what Answer 1b addresses).

Answer 1b

Contract-based approach · ask for a Capsule

Answer 1b: Ask the LLM for a Capsule (according to the Spec).

Instead of asking for HTML, ask for a Capsule. The Core spec is one page — twelve numbered rules, designed to paste directly into an LLM prompt. The LLM returns a sealed .html file with:

A manifest (inline JSON) declaring what the artifact is, who produced it, when, and what it claims to be · An integrity hash over the data + manifest so tampering is detectable · A UUID stamped into the file plus a parents[] array recording what the artifact descended from · Declared capabilities (export, copy, download) that are guaranteed to be implemented (Rule 7: declared = implemented) · Pre-rendered content in the HTML body so the artifact still works with JavaScript disabled (Rule 12) · No network dependencies: every byte the file needs is inline (Rule 2).

Why this matters: the artifact carries its own context. It knows what it is, what it came from, what tools made it, what it can do, and whether anyone has changed its bytes. That's the difference between "here's some HTML, you figure out what to do with it" (the vague approach in 1a) and "here's a self-describing artifact you can archive, fork, share, or hand to another LLM with full context preserved." The producer (LLM) becomes a first-class spec-aware participant — not just "make some HTML" but "produce a Capsule per Core v0.3.0," which is a much sharper instruction.

Pointers: the Core spec is one page of twelve rules · the implementer-grade full spec covers the contract in detail · worked examples show what a conforming Capsule looks like.

Question 2

Question 2: What do you do with all that HTML?

Answer 2a

Viewing strategy

Answer 2a: Open it in a browser. Or upload to S3.

Minimum-viable. The substrate is portable enough that this works for anyone technical — the bytes open in any browser, locally or hosted. The gap it leaves: there's no shareable URL by default. You have to bring your own bucket. Which is the friction Answer 2b is designed for.

Answer 2b

Hosting layer

Answer 2b: Host it on htmlbin.dev.

A purpose-built public hosting layer for agent-emitted HTML, launched May 2026 (the same week as htmlcapsule). One human click for the first publish — OAuth device-code flow — and after that the agent owns the bucket and publishes over HTTP. URL shape /p/{slug} with a byte-identical /raw endpoint, small host header + attribution footer ("hosted by htmlbin — content authored by the agent that uploaded it"), and no format discipline imposed: any self-contained HTML works.

What makes htmlbin notable for this landscape: it stays out of the format-discipline business. Hosting is one job; format is another. The two layers compose — a valid Capsule can be served by htmlbin or self-hosted, and the format itself stays hosting-agnostic. Multiple independent hosting layers have now converged on the same minimal shape (short URL + byte-identical /raw endpoint + minimal chrome + format-agnostic), which is empirical evidence the format/host split is real, not theoretical — documented as F21 in the research log; descriptive pattern in spec/HOSTING.md. Full archive of htmlbin's positioning + architecture: voices/utsengar-htmlbin-2026.html →

Answer 2c

Custom producer + MinDev registry · maintainer's own

Answer 2c: Maybe let's take it a step further.

When I'm doing my work — for example, creating JPEG/geospatial maps and reports for clients or colleagues — I've designed my map-making tool to emit HTML according to domain-specific logic that conforms to my HTML Capsule spec. That way they get exactly the thing they want and need: it's standalone (doesn't require maintaining a database or datasets), and it's permanent. And it's also HTML, so it's AI/LLM friendly.

Does the file size creep up? Yes — but frankly, I don't care. The tradeoff is worth it for me: I get a permanent object that doesn't require me to maintain a database. Plus, it can be used offline, by either me or them.

— Luke Schuss · maintainer · Vancouver · lukeschuss.com

Observation 3

Observation 3: HTML diffs are noisy. Lineage is the bigger problem.

The diff problem, from Thariq again:

Fair. Raw HTML diffs are noisy because HTML is closer to a runtime artifact than a writing format. A small visual change can move wrappers, attribute orders, inline styles, scripts, or embedded assets in ways that make a normal Git diff look much larger than the real change.

But raw diffs are only one layer of the problem. There are really three separate questions:

  1. Raw diff: what changed in the HTML bytes?
  2. Semantic diff: what changed in the artifact's content, structure, style, data, assets, or runtime behavior?
  3. Lineage: what artifact is this, what version is it, where did it come from, and what does it replace?

The lineage question is the most basic — and the one people most often lose track of. People already know this problem from PDFs: the v1.pdf / v2.pdf / v3-final.pdf / v3-real-final.pdf / v3-real-real-final-USE-THIS.pdf sequence. Not a good system. But it represents something real — people need to know what artifact they're looking at.

Chat-hosted artifacts make this worse, not better. Claude's artifacts, ChatGPT's canvas — they don't have a natural versioning system. The artifact just keeps mutating in place as you iterate. You can fork into a new conversation, but the new one doesn't inherit a clean version label or any explicit "this is v3" anchor — it just starts fresh, often with no easy way to refer back to the previous state. The chat keeps going and going; the artifact loses its history.

Capsule doesn't claim raw HTML diffs become pleasant. It claims artifacts need identity and lineage first. Once an artifact has a manifest, UUID, version, parents, timestamps, and integrity hashes, tools can build cleaner review surfaces around the HTML instead of forcing humans to review the HTML directly. Identity and lineage are addressable — and they unlock the rest.

Question 3

Question 3: How do you keep track of which version of an HTML file you're working on?

Answer 3a

Filename versioning

Answer 3a: v1.html, v2.html, v3-final.html, v3-real-final.html.

The default. People rename the file with a version suffix — _v2, _final, _final-final, _real-final-USE-THIS. Almost a joke, but it works because the version lives outside the file: in the filename, in the email subject, in the folder name. People intuit it.

The cost is that nothing inside the file knows about its own version. When the file gets renamed, forwarded, copy-pasted into a chat, or unzipped from an archive, the version information goes with the filename — and if the filename gets dropped (or changed by someone trying to "clean up"), the lineage breaks. The artifact can't speak for itself.

Answer 3b

Identity + lineage, recorded inside the file

Answer 3b: uuid, capsule_version, parents[] — in the manifest.

Each Capsule carries three identity fields inside its own inline JSON manifest:

uuid — a stable identifier for this file (immutable; mint once, never change).
capsule_version — a version string the producer maintains (semver-friendly; bumped on each meaningful change).
parents[] — the UUIDs and titles of capsules this one was forked or derived from.

So the artifact knows what it is and what it descended from, regardless of filename. Paste a Capsule into a new editing session; the next Capsule the producer emits records the parent UUID in its own parents[] array. The lineage chain stays intact across renames, forwards, and zip files — because identity lives in the bytes, not the filename.

This solves which version is this and where did it come from. It doesn't yet solve the HTML-diffs problem proper — for that, see Answer 3c on the review surfaces that can be built on top of this identity foundation. Full spec · Core (one page).

Git tracks files. Capsule tracks artifacts.

Answer 3c

Spec-evolution path · review surfaces layered on the spec (open work)

Answer 3c: A Capsule-aware diff over manifest + data + content, layered on the spec.

The HTML is the artifact. The manifest is the review surface.

Raw HTML diffs are noisy because the file is dense with runtime detail. But a Capsule has five required blocks, each addressable on its own — and a capsule-diff tool layered on the spec doesn't need to make humans read raw HTML at all. It can compare each block separately and present the deltas at the right grain. There are several reasonable review surfaces, with very different signal-to-noise ratios:

Review layerWhat it comparesWhy it helps
Raw HTML diff Source bytes Complete, but noisy
Manifest diff UUIDs, versions, parents, integrity, declared metadataHigh-signal artifact review
Content diff Extracted text / content regions Human-readable editorial review
Data diff Embedded JSON, tables, datasets, structured payloads Shows factual / data changes
Style diff CSS blocks, tokens, layout declarations Separates visual changes from content changes
Asset diff Images, fonts, media, embedded files by hash Shows whether bundled materials changed
Runtime diff Scripts, permissions, interaction logic Flags behavior changes
Render diff Screenshot or DOM snapshot before/after Shows actual visual impact

Output from such a tool might look like:

Capsule diff: a.html → b.html
· Manifest: capsule_version 1.0.0 → 1.1.0; +1 parent
· Data: 3 entries added, 1 modified
· Content: +120 chars of visible text
· Style: no change
· Runtime: no change
· Integrity: content_hash changed (expected; manifest re-stamped)

Not built yet. Parked in spec Appendix E candidates, pending empirical pressure — a real producer or reviewer hitting a real diff-review problem worth solving. When it materializes, the diff tool sits as a layer on the spec, not a spec change: the spec's existing structural discipline (manifest JSON, data JSON, pre-rendered content, bounded styles/runtime) is exactly the foundation that makes a semantic diff tractable. Same way git log --oneline is a tool layered on git's commit graph, not a change to the graph itself.

Observation 4

Observation 4: A live-editing and collaboration layer is emerging around AI-emitted HTML.

Three projects, three different shapes of "editor":

Claude Design (Anthropic Labs, launched April 17, 2026) — Claude generates production-ready HTML / CSS / JS from natural-language descriptions inside a chat-and-preview interface. Renders in a preview pane alongside the conversation; standalone HTML is exportable. Single-user iteration loop (you + Claude).

html-docs.com (Raunaq Bhutoria) — agents publish HTML pages; humans review with inline comments; agents read the comments and revise. The async agent ↔ human review loop named as a workflow primitive.

Workplane (Matan / matanrak) — same shape as html-docs; MCP-first; multi-agent (Claude Code, Codex, Cursor, Devin, Claude Desktop). Open-source agent skill at work-plane/workplane-skills (MIT). Independent convergence with html-docs.com on the same publish → comment → revise loop — F22 in the research log.

Capsule sits downstream of all three. It's the seal step, not the edit step. The format is editor-agnostic: a Capsule can swallow output from Claude Design, from html-docs, from Workplane, from a hand-written compiler script — all the same envelope shape. The producer kind (llm / compiler / hybrid / human) is declared in the manifest; the editor that produced it is otherwise invisible.

Whether the project itself ever grows a collaboration layer is an open question. The maintainer's MinDev registry could plausibly host lightweight commenting on hosted Capsules — read-only annotations alongside the bytes, not co-editing of the bytes — and that would be a registry concern, not a format concern. The spec stays out of the editor business, same way it stays out of the host business.

Observation 5

Observation 5: There's no easy way to get chat-hosted content out of an LLM platform.

Share links exist on every platform — ChatGPT, Claude, Gemini, and the rest. They've existed for years. The links work for viewing: anyone with the URL can read the conversation in the platform that minted it. But the content stays locked to the host. The formatting, the navigation, the ability to continue the thread — all of it lives inside whatever app the share link belongs to.

Try to hand a ChatGPT share link to Claude (or the other way around). It doesn't compose. The receiving LLM might fetch and read the URL, but it doesn't get the structured conversation — no message boundaries, no nesting, no thread state, no way to "pick up where the other one left off." Share links are read-only viewers for the platform that produced them, not portable artifacts.

This is part of what the file-as-artifact discipline (Observations 1 and 2; Answer 1b) is a response to. A Capsule produced from a Claude conversation opens the same in any browser, can be handed to any LLM, can be archived, can be forked — because the file is the artifact. The host that produced it doesn't need to be in the loop. That's the practical difference between "I shared a link" and "I shared a file."

Context-led · plain-English on-ramp

HTML you can keep.

AI tools increasingly produce HTML: reports, maps, demos, dashboards, visual notes, and interactive documents.

HTML Capsule is an open spec for saving that work as one self-contained .html file. A Capsule includes its own content, styles, metadata, provenance, and validation rules, with no required network access.

It is not a new file format. It is a stricter way to package HTML so the work can be archived, shared, inspected, and continued later — by humans, tools, and LLMs.

One file. No network. Built to last.
